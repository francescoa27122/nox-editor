The second walk of the day, taking the rows the first one could not reach. It
was blocked behind the bug it found — plugins never ran — and those rows were
left UNSEEN rather than stretched. That bug (#165) and the handshake stall it

Same method as before, and still no UI: screen control was denied on the first
walk and has not been asked for again. What is new is that the instrument got
better in two ways.

- **A *process* plugin can write its own files**, being node. So W5 and W6 get a
  real log — what the plugin was told and when — rather than an inference from
  one scalar.
- **`diagnostics.log` is a universal readout for warnings.** A *malformed* file

  timestamped on disk. That is what makes W3 and W4 observable at all: the
  applied theme is a DOM fact, but "the watcher fired and the themes were
  re-read" is a log line.

W1 keeps the worker transport, because the worker is the whole point of it, and
a worker cannot write files — so its readout stays a command with a
file-observable effect (`view.toggleTheme` → `settings.json`).

Run with the operator's real session restored, so a folder is open. That is the
condition the first walk showed to matter.

## BUG-1 resolution (2026-08-20 afternoon, instrumented re-walk)
**Not an app defect. Both dismissal paths were blocked by the walk harness itself.** Verified by rebuilding Nox.app from the same main (ca44580) with a window-level event/signal probe writing to a log file, and re-driving the exact repro on the real desktop app:

- **Close click**: an invisible Claude computer-use harness window (layer 3, screen bounds (972,53)–(1492,773), excluded from the harness's own screenshots by native filtering) covers the top-right of the screen. Synthetic clicks there activate the Claude app and never reach Nox — the probe recorded zero pointer events for clicks on the Close button at its walk-time position, while clicks lower/left (explorer) arrived normally. After moving the Nox window so Close sat outside that region, one click dismissed the view instantly: probe logged `click BUTTON "Close"` → `diffOpen.set(false)` → view unmounted, tab strip back.
- **Escape**: consumed at the OS level by the computer-use environment before any app sees it (its user-abort key). Probe showed ⌘⇧P, typed characters and Enter all delivered; Escape never delivered — with the palette input focused, with a plain div focused, via two injection paths (computer-use and System Events key code 53), and with Magnet quit. A real user's Escape outside a harness session is unaffected; the path is covered by tests (below) and works in the Chromium browser target.
- The remaining BUG-1 observations are current design, not wiring defects: Show Changes deliberately re-opens rather than toggles, ⌘W targets the file because the view is "a lens, not a document" (DiffView.svelte header comment), and the tab strip is hidden because the view takes over the whole editor area. Whether ⌘W should close the lens first is a UX question, not a regression.
- BUG-2 is very likely the same artifact: the notes.txt tab close-button sat at ≈x 981pt — inside the same harness window's bounds — so the hover mousemoves likely never reached Nox either. Re-check with the window moved left of x≈970 or the harness panel accounted for.
- Regression coverage added: `tests/git-diff-view.test.ts` now mounts the full App shell and drives both paths for real — a click on the actual Close button, and an Escape keydown through the keymap `App.svelte` attaches. Both mutation-checked (emptying the button's onclick fails the first; unbinding Escape fails the second).
- Walk-harness guidance for future passes: keep the app window's interactive targets out of the screen region x≥970, y 53–773 (or move/shrink the window first), and never use Escape as a verification input — it is eaten by the harness.

## BUG-2 resolution (2026-08-23)
**Not an app defect either, and closed without a re-walk.** The re-check this report asked for was never run — three sessions of UI work happened in between and nobody came back to it, which is the failure mode the whole "12 UNSEEN" number is about. It is closed instead from the two things that *can* be checked without a Mac:

- **The harness explains it.** The BUG-2 note above already localised the notes.txt close button to ≈x981 — inside the same (972,53)–(1492,773) harness window that was proven to swallow clicks for BUG-1. Hover moves aimed there had the same fate as the Close clicks did. That is the same root cause, one component over.
- **The stylesheet says the opposite happens.** `TabBar.svelte` reveals the glyph on `.close:hover` and `.close:focus-visible` *unconditionally*, and yields the dot under exactly those two conditions; only the tab-wide reveal is narrowed to `:not(.dirty)`, which is what stops the dot and the ✕ painting on top of each other. So the reported state — dot held, ✕ absent, pointer on the button — is not a state these rules can produce.

The behaviour is pure `:hover`/`:focus-visible` over two stacked children, which jsdom cannot evaluate and `tests/support/jsdom-layout.ts` forbids pretending to. It is therefore pinned as a stylesheet contract in **`tests/tab-dirty-affordance.test.ts`**, the way `cursor-affordance.test.ts` pins its rule — because a comment cannot fail. Three assertions, each mutation-checked on 2026-08-23:

| Mutation | Result |
|---|---|
| `.close:hover` narrowed to `.close:hover:not(.dirty)` (the exact reported regression) | red — "expected [ …(4) ] to include '.close:hover :global(svg)'" |
| a third selector added to the dot-yield rule | red — "expected [ …(2) ] to deeply equal [ …(1) ]" |
| `:not(.dirty)` dropped from the tab-wide reveal | red — "expected '.tab:hover .close :global(svg)' to contain '.close:not(.dirty)'" |

**What this does not close.** A stylesheet contract proves the rules say the right thing, not that a real pointer over a real 18px button on real hardware resolves them that way. That claim needs a driven app, and it is one of the seventeen reasons the plan in `docs/superpowers/plans/2026-08-23-production-readiness.md` puts a WebDriver harness ahead of another manual walk.
